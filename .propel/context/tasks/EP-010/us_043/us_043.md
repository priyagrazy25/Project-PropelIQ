# User Story - US_043

## Story ID
- ID: US_043

## Story Title
- PHI Encryption At Rest & In Transit

## Description
- As a system administrator, I want all Protected Health Information encrypted using AES-256 at rest and TLS 1.2+ in transit, so that the platform meets 100% HIPAA-compliant data handling requirements.

## Acceptance Criteria
1. **Given** PHI is stored in the database, **When** encryption at rest is configured, **Then** SQL Server Transparent Data Encryption (TDE) is enabled and column-level encryption is applied to sensitive fields (PasswordHash, clinical data, insurance details) per FR-030 and NFR-005.
2. **Given** clients connect to the API, **When** requests are made, **Then** all client-server connections enforce TLS 1.2 or higher per NFR-006.
3. **Given** the backend connects to external services (SendGrid, Twilio, Calendar APIs), **When** outbound requests are made, **Then** all server-external-service connections enforce TLS 1.2+ per NFR-006.
4. **Given** clinical document files are stored, **When** saved to disk, **Then** the EncryptedFilePath in DR-004 references AES-256 encrypted file content.
5. **Given** any endpoint, **When** a connection attempt uses a protocol below TLS 1.2, **Then** the connection is rejected.

## Edge Cases
- What happens if TDE is temporarily unavailable during a database restart? (Database remains offline until TDE is re-initialized; no unencrypted reads are possible)
- What if a legacy client attempts to connect with TLS 1.0/1.1? (Connection is refused with a clear error indicating minimum TLS 1.2 requirement)
