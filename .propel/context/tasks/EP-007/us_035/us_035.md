# User Story - US_035

## Story ID
- ID: US_035

## Story Title
- 360-Degree Patient View Generation

## Description
- As a clinical staff member, I want the system to generate a unified 360-Degree Patient View by aggregating and de-duplicating extracted data across all uploaded documents for a patient, so that I can see a single consolidated clinical profile with tabbed sections.

## Acceptance Criteria
1. **Given** a patient has multiple processed documents, **When** the 360-view is generated, **Then** extracted data is aggregated across all documents with semantic de-duplication merging equivalent entries (brand vs. generic medication names) per AIR-002.
2. **Given** the aggregation engine runs, **When** retrieving context, **Then** the RAG pipeline retrieves top-5 relevant chunks with cosine similarity >= 0.75 per AIR-R02.
3. **Given** retrieved chunks, **When** re-ranking runs, **Then** hybrid re-ranking combines semantic similarity with source document recency weighting (newer documents weighted 1.2x) per AIR-R03.
4. **Given** structured output is produced, **When** validation runs, **Then** 99% or higher schema validity is maintained against predefined JSON schemas per AIR-Q03.
5. **Given** the 360-view is generated, **When** a user accesses it, **Then** it renders within 3 seconds leveraging Upstash Redis caching with 15-minute TTL per NFR-004 and NFR-017.
6. **Given** the 360-view UI, **When** displayed, **Then** it presents tabbed sections: Vitals, Medical History, Medications, Allergies, Lab Results, Diagnoses per DR-006.

## Edge Cases
- What happens when a patient has only one uploaded document? (360-view generates from single-source data; no conflict detection needed; sections may be partial)
- What if the Redis cache is unavailable? (View falls back to direct database generation with degraded performance; cache miss is logged)
