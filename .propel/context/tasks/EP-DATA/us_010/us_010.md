# User Story - US_010

## Story ID
- ID: US_010

## Story Title
- Data Integrity & Validation Rules

## Description
- As a developer, I want database-level referential integrity with cascading soft-delete, unique constraints preventing double-booking, and confidence score validation, so that the data layer enforces consistency and prevents invalid states without relying solely on application logic.

## Acceptance Criteria
1. **Given** foreign key relationships are configured, **When** a patient-related record is deleted, **Then** the system performs a soft-delete by setting Status = Deactivated rather than hard-deleting, preserving referential integrity per DR-008.

2. **Given** unique constraints are applied, **When** two requests attempt to book the same ProviderID+DateTime slot simultaneously, **Then** the database-level row lock prevents double-booking and the second request receives a conflict error per DR-009.

3. **Given** User.Email has a unique constraint, **When** a duplicate email registration is attempted, **Then** the database rejects the insert with a unique constraint violation.

4. **Given** confidence score validation is configured, **When** an ExtractedData record is inserted with a ConfidenceScore outside 0.0-1.0, **Then** the database CHECK constraint rejects the insert per DR-010.

5. **Given** low confidence flagging is implemented, **When** an ExtractedData record has ConfidenceScore below 0.7, **Then** the record is automatically flagged as "Low Confidence" in query results for the 360-Degree Patient View.

## Edge Cases
- What happens when cascading soft-delete encounters a circular reference? (EF Core configuration prevents cascade cycles; deepest child is soft-deleted first)
- How does the system handle orphaned records from failed transactions? (Background cleanup job identifies orphaned records weekly and flags for admin review)
