# User Story - US_005

## Story ID
- ID: US_005

## Story Title
- AI Runtime & Orchestration Setup

## Description
- As a developer, I want Ollama deployed locally with the Phi-3-mini 3.8B model and Semantic Kernel configured as the .NET orchestration layer, so that the platform can support conversational intake, clinical data extraction, and medical code mapping without transmitting PHI externally.

## Acceptance Criteria
1. **Given** the AI runtime is installed, **When** I start Ollama, **Then** the Phi-3-mini 3.8B model loads successfully and responds to inference requests via HTTP on localhost.

2. **Given** Semantic Kernel is configured, **When** I register AI services in the DI container, **Then** prompt management, conversation memory, and tool calling functions are available through typed interfaces.

3. **Given** model versioning is required, **When** I deploy a new model version, **Then** the previous version is retained alongside the active version in the Ollama registry, enabling rollback within 15 minutes.

4. **Given** the AI infrastructure is running, **When** I send a test inference request, **Then** the response is returned within the configured token budget limits (4,096 for conversational, 8,192 for extraction).

5. **Given** AI safety is critical, **When** AI services are registered, **Then** custom .NET middleware validates JSON schema output, enforces confidence thresholds, and applies token budget limits on all AI requests.

## Edge Cases
- What happens when Ollama crashes during inference? (Circuit breaker triggers after 3 failures in 60 seconds; system degrades gracefully with AI features disabled)
- How does the system handle model corruption? (Health check detects model load failure; previous version is auto-loaded from registry)
