# User Story - US_004

## Story ID
- ID: US_004

## Story Title
- Caching & Real-Time Infrastructure

## Description
- As a developer, I want Upstash Redis free tier configured for distributed caching and SignalR WebSocket hub established for real-time client-server communication, so that the platform delivers sub-second slot availability updates and reduces database load by 60%.

## Acceptance Criteria
1. **Given** the caching layer is configured, **When** the application starts, **Then** it connects to Upstash Redis via HTTPS-only protocol with proper authentication.

2. **Given** the three-tier caching strategy is implemented, **When** I inspect cache configuration, **Then** L1 (slot availability, 30s TTL), L2 (patient profiles, 5min TTL), and L3 (360-degree views, 15min TTL) tiers are configured with event-driven invalidation.

3. **Given** SignalR is configured, **When** a client connects via WebSocket, **Then** the SignalR hub establishes a persistent WSS connection for real-time message delivery.

4. **Given** a booking event occurs, **When** slot availability changes, **Then** the SignalR hub broadcasts the update to all connected clients within 500 milliseconds.

5. **Given** Redis free tier limits apply, **When** the 10K commands/day threshold is approached, **Then** the application falls back to local in-memory caching with configurable TTL.

## Edge Cases
- What happens when Upstash Redis is unreachable? (Circuit breaker opens; application falls back to in-memory cache with degraded performance)
- How does the system handle SignalR reconnection after network interruption? (Client auto-reconnects with exponential backoff; missed updates are reconciled via REST fallback)
